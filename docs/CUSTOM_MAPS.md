# Custom battlefields

RimRTS lets the match screen choose how the skirmish map is built. There are two
modes, and they share the same match flow (squad, teams, budget, drop into the map):

| Mode | What decides the map | Where it is configured |
| --- | --- | --- |
| **Biome battlefield** | A flat planet tile of a curated biome, generated by vanilla map generation with a chosen rectangular size | Biome cards + width/height controls on the match screen |
| **Hand-authored map** | A `PrefabDef` shipped with the mod, stamped onto the generated map | `Defs/Prefabs/*.xml`, generated by `tools/generate_battlefield_prefabs.py` |

Both modes still land on a real planet tile, so world generation, factions and the
squad flow are unchanged. The generated map is then resized/replaced before the
player's pawns are spawned.

## The 10,000 ft view

`Page_ChooseBiome.DoNext` calls `BattlefieldLayout.Begin(size, prefab)` and starts
the match. `Source/Patches/MapGeneratorPatch.cs` is a Harmony patch on
`Verse.MapGenerator.GenerateMap`:

- its **prefix** replaces the square `IntVec3 mapSize` argument with the chosen
  `BattlefieldLayout.Size` (this is how rectangular maps work);
- its **postfix** hands the finished `Map` to `BattlefieldLayout.Apply`, which — for
  a hand-authored map — clears the procedurally generated things, centers the
  prefab and stamps it with `PrefabUtility.SpawnPrefab`.

The layout is consumed exactly once, so every other map in the game (quests,
pocket maps, future caravan maps) is generated untouched. (less prone to breaking)

## Rectangular biome maps

Vanilla only offers square map presets in its UI, but the engine itself is not
square-only: `MapGenerator.GenerateMap` receives an `IntVec3` size, and `Map.Size`
is an `IntVec3`. The match screen exposes:

- **Width** / **Height**: 60–250 cells, in steps of 10;
- **Square** (150×150), **Wide** (220×120), **Tall** (120×220) presets.

Caveats worth testing whenever a new map size is used:

- A few vanilla generation steps (rivers, caves, geysers) were tuned for roughly
  square maps; battles are still winnable, but extreme aspect ratios can put an
  objective or a river ford far from the drop zone.
- Edge drop pods use the map edges, so very wide maps give a longer approach.

If a size turns out to be problematic, keep the default 150×150 and use a
hand-authored map for that battle instead.

## Hand-authored maps

Any `PrefabDef` whose `defName` starts with `RimRTS_` is listed on the match screen
(`Source/Skirmish/BattlefieldPrefabs.cs`). Restricting by prefix is deliberate:

- DLC prefabs (props, ancient rooms, quest sites) are not battlefields;
- if the DLC that defines a prefab is absent, the list simply does not include it;
- a third-party mod can ship a battlefield by using the same prefix.

The prefab's own `<size>` becomes the map size. Authored content is expected to
cover the whole battlefield, so the game first removes the procedural things
(`map.listerThings.AllThings`), then stamps terrain and things from the prefab at
the centered origin. Authored terrain wins over generated terrain; authored things
win over generated things.

Constraints (the screen refuses and logs a clear error otherwise):

- prefab size must be 20–400 cells per side;
- the prefab must actually fit in the map it will be stamped into (it is stamped
  into a map generated at exactly the prefab's size, so this is guaranteed);
- a malformed prefab or a failed stamp is logged and the match continues on the
  procedural map instead of breaking the game start.

## Authoring workflow

Hand-writing thousands of prefab coordinates is error-prone, so layouts are
generated from small rules by a script:

```powershell
# any Python 3.9+ interpreter works
python tools/generate_battlefield_prefabs.py
```

Output: `Defs/Prefabs/RimRTS_RiverCrossing.xml` and
`Defs/Prefabs/RimRTS_UrbanBlocks.xml`. Treat those files as build output: edit the
rules in the script, rerun it, and commit the regenerated XML.

The script validates before writing:

- every rectangle and position is inside the prefab bounds;
- the first terrain layer covers the whole prefab (so no cell is left without
  terrain);
- no two things are spawned on the same cell;
- the generated XML parses back cleanly with `xml.etree`.

To add a battlefield:

1. add a `Battlefield(...)` builder function next to `river_crossing()` /
   `urban_blocks()`;
2. register it in `main()`'s tuple;
3. pick a `defName` starting with `RimRTS_`;
4. run the script and check the generated XML diff.

Rules you can use from Python:

- `field.paint(terrainDef, x1, z1, x2, z2)` — paint an inclusive rectangle of
  terrain; later paints win (that is how fords are painted after the river);
- `field.wall_line(...)`, `field.wall_ring(...)` — wall runs with optional door
  gaps;
- `field.scatter(thingDef, count, surfaces, rng, clearance=...)` — deterministic
  scatter that only lands on the given terrain and never overlaps other things;
- `field.terrain_at(x, z)` — query the painted terrain, for example to keep rubble
  out of water.

## Prefab XML reference

Only the subset the tooling emits is documented here; `PrefabDef` supports more.

```xml
<PrefabDef>
  <defName>RimRTS_RiverCrossing</defName>
  <label>River crossing</label>
  <size>(100,140)</size>
  <terrain>
    <Soil>
      <chance>1</chance>
      <rects><li>(0,0,99,139)</li></rects>
    </Soil>
  </terrain>
  <things>
    <Wall>
      <stuff>BlocksSlate</stuff>
      <hp>280</hp>
      <positions><li>(6,0,6)</li></positions>
    </Wall>
  </things>
</PrefabDef>
```

- `<size>(width,height)</size>` — IntVec2.
- Terrain rectangle syntax is an **inclusive corner pair**:
  `<li>(x1,z1,x2,z2)</li>` covers `x1..x2` and `z1..z2`. Terrain nodes are applied
  in document order, so paint base ground first and overlays later.
- Things: `<positions>` takes `(x,0,z)` cells; `<position>` takes a single cell;
  `<rects>` takes corner pairs like terrain and spawns one thing per cell;
  `<stuff>` and `<hp>` are optional; `<chance>`/`<rotations>` exist in vanilla
  prefabs but are not required.
- Explicit `<chance>1</chance>` on terrain is emitted on purpose: it makes the
  authoring intent readable and avoids surprise when the default changes.

## In-game authoring (optional)

If you prefer building a battlefield in-game instead of writing rules, the vanilla
dev-mode prefab tools can capture a selection into a `PrefabDef`:
enable dev mode, build the layout, then use the prefab debug actions
(`PrefabUtility.CreatePrefab`) to create a prefab from the selection. Copy the
generated def into `Defs/Prefabs/`, rename it with the `RimRTS_` prefix, and keep
the `<size>` consistent with the captured area.

## Troubleshooting

- **A prefab is not listed**: `defName` must start with `RimRTS_`; the XML must be
  under `Defs/` (any subfolder) and must parse.
- **"…is 120x120 but the map is …"** in the log: the map was generated at a
  different size than the prefab expects. The match screen sizes the map from the
  prefab, so this only happens if something else changed the map size first.
- **Terrain looks vanilla**: the prefab terrain is applied after generation, so a
  missing/failed stamp is logged; check the log for the `[RimRTS]` lines.
- **Things are missing**: the mod clears generated things before stamping; if the
  prefab spawn fails (bad def name, bad stuff), the error is logged with the
  prefab name.
